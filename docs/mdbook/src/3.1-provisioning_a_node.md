# Provisioning a Node

## Requirements

- A Talos node in maintenance mode on your network
- A Node resource in Kubernetes
- A Cluster resource that the node can reference [(see the next section)](./4-cluster_resource.md)

> [!NOTE]
> Creating a Node, by itself, will do nothing to the node in maintenance mode. It is simply a declaration of intent to manage a Talos node. Once you run a provisioning operation, the Talos Operator will take over management of the Node.

## Effective config

If the Node resource is valid, the operator will generate a `status.effectiveConfig` field containing the Talos configuration that will be applied to the node upon provisioning.

Double-check this field to make sure the configuration looks correct before proceeding.

## Provisioning

With kubectl:

```sh
kubectl patch nodes.talos.rtl.de {{NODE_NAME}} --type=merge \
  -p '{"operation":{"type":"Provision","provision":{"address": "10.256.2.54"}}}'
```

or, you can create it in the Node resource manifest during a `kubectl apply`:

```yaml
apiVersion: talos.rtl.de/v1alpha1
kind: Node
metadata:
  name: athena-h1
  namespace: athena-production
spec:
  clusterRef: athena
  role: controlplane
operation:
  type: Provision
  provision:
    address: 10.256.2.54
```

Please take care not to check anything with an `operation` field into version control, as this field is intended to be transient.

### Bootstrapping

Automatic cluster bootstrapping should automatically bootstrap the cluster once the first control plane node is provisioned and ready.

If you want to manually trigger the bootstrap, you can run a `Bootstrap` operation on the Node or Cluster resource:

```yaml
operation:
  type: Bootstrap
```

> [!IMPORTANT]
> Only one control plane node should be bootstrapped. Other control plane nodes will join the bootstrapped node's etcd cluster.

## Adopting existing nodes

If you have an existing Talos node that you want to bring under control of the Talos Operator, you can use the `Provision` operation with the `skip` flag set to `true`. This will bypass any maintenance-mode configuration applies and immediately set `Provisioned` to `True`.

```yaml
operation:
  type: Provision
  provision:
    skip: true
```

> [!IMPORTANT]
> **If the Cluster is within its maintenance window**, a RollingApply may be triggered automatically if the deployed configuration does not match the effective configuration.

### Adopting an existing cluster

The process to adopt an existing cluster is much the same as adopting an individual node:

- Create a Secret containing the cluster's `secrets.yaml`
- Create a Cluster resource that references the Secret and patches/patchRefs that match the existing cluster configuration
- Create Node resources for each node in the cluster and patches/patchRefs that match node-specific configuration
- For each Node, run a `Provision` operation with `skip: true`

## Monitoring

The operation is copied into `status.operationStatus`, and the `operation` field itself is cleared immediately.
You can monitor the progress of the operation by watching the `status.operationStatus.phase` field:

```sh
watch kubectl get nodes.talos.rtl.de {{NODE_NAME}}
```

Specifically,

- the `status.operationStatus.type` should be `Provision`,
- the condition `Provisioned` should eventually be `True`,
- and the `status.operationStatus.phase` should eventually be `Done`
