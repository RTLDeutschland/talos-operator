# Automatic etcd backups

The Cluster reconciler can be configured to automatically create S3-backed etcd backups for a cluster.

To do this, configure the `spec.options.etcdBackup` block in your Cluster manifest:

```yaml
spec:
  options:
    etcdBackup:
      enabled: true
      # prefix: ""
      # interval: 4h (default 4h)
      credentialsSecretRef:
        name: etcd-backup-credentials-aws
        # namespace: talos-operator-system (optional, defaults to current namespace, can be disabled)
      # encryption:
      #   age:
      #     recipients:
      #       - age1gszn7e8xsf6hh26wq6jse06kmctdhxg240xkgdd5g5t8j605yaaqprpwre
```

The time of the last successful etcd backup can be found in the status of the Cluster resource as `status.lastEtcdBackup`.

### Secret format

The secret format looks like this:

```go
// ClusterEtcdBackupSecret is the expected data structure for a Kubernetes secret containing etcd backup credentials.
type ClusterEtcdBackupSecretData struct {
	AWSAccessKeyID     string `mapstructure:"AWS_ACCESS_KEY_ID"`          // required
	AWSSecretAccessKey string `mapstructure:"AWS_SECRET_ACCESS_KEY"`      // required
	AWSSessionToken    string `mapstructure:"AWS_SESSION_TOKEN,omitzero"` // optional
	AWSEndpoint        string `mapstructure:"AWS_ENDPOINT,omitzero"`      // default from minio client
	AWSRegion          string `mapstructure:"AWS_REGION,omitzero"`        // default from minio client
	AWSS3Bucket        string `mapstructure:"AWS_S3_BUCKET"`              // required
	GlobalPrefix       string `mapstructure:"GLOBAL_PREFIX,omitzero"`     // optional
}
```

### Prefixes

The `prefix` field in Cluster is additive to the secret's `GlobalPrefix`, and the combined prefix is additive to the existing structure.

For example, if the global secret prefix is set to `hello-` and the Cluster prefix is set to `world`, the output would look something like:

```
# <prefix>/<namespace>/<name>/<timestamp>.snap.zst[encryption]
hello-world/sapphiccode-talos/athena/<timestamp>.snap.zst.age
```

At the very minimum, the secret must contain the `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_S3_BUCKET` fields.

> [!important]
> It is **strongly recommended** to set a lifecycle policy on this bucket so etcd backups are eventually expired.
> The Talos operator does not concern itself with the lifecycle of the created backups.

### Security concerns

If you want to disable cross-namespace backup secret access, set the Helm value `features.enableCrossNamespaceBackupCredentialsRefs` to `false`.

## Restoring from backups

To restore from backups:

1. Set the cluster option `spec.options.autoBootstrap` to `false`.
    - If there are remaining controlplanes, reset them with `--graceful=false` and (recommended) `--cloud-reset` using `kubectl talos reset`.
2. Acquire your etcd snapshot from the S3 bucket.
    - Decrypt it with `age -i <your identity file> -o etcd.snap.zst --decrypt <encrypted file>` [(link)](https://age-encryption.org) (if encrypted)
    - Decompress it with `zstd -d` [(link)](https://github.com/facebook/zstd)
3. [Provision](./3.1-provisioning_a_node.md) all your controlplanes, do not bootstrap them.
4. Ensure talosctl is up to date. [(link)](https://github.com/siderolabs/talos/releases)
5. Use `kubectl talos talosctl -n <cluster namespace> <cluster controlplane node> -- bootstrap --restore-from=<decrypted-uncompressed-snapshot>` to bootstrap the cluster again, from the snapshot.
6. Hopefully, watch your cluster recover and reach a healthy state.
